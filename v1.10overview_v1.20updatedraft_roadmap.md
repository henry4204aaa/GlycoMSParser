## 1. What this document is

`README.md` describes what GlycoMSP *does*. This document describes **where the project stands and
where it is going** — written for thesis committee members, manuscript reviewers, and collaborators
who need to see the development direction rather than the usage instructions.

It has two halves, and they are deliberately kept apart:

- **§3 – §7 — v1.10, what exists today.** Statements here describe shipped behaviour.
- **§8 – §9 — v1.20 and beyond, what is intended.** Nothing here is implemented. Items are proposals
  awaiting prioritization.

Anything not traceable to the current source or to the freeze record is marked as such. See §11 for
the provenance of every class of claim in this document.

## 2. Version scheme

GlycoMSP uses a **two-digit decimal version scheme** — `MAJOR.MINOR`, with the minor field always
written to two digits, and an optional third field for incremental work within a line (`1.09.4`).
Releases order as:

```text
1.09  <  1.10  <  1.20  <  1.21  <  1.30
```

This is stated explicitly because the abbreviated forms are ambiguous. **`v1.10` is the 1.1 line** —
the release prepared for publication — **not** the tenth point release after 1.9. Likewise `v1.20`
and `v1.2` denote the same release. The two-digit form is used throughout this document and for
release tags, because it orders correctly both under a plain decimal reading and under the
major/minor convention that packaging and version-sorting tools assume — whereas the abbreviated
`1.2` would sort *before* `1.10` in those tools.

The in-source changelog still uses the abbreviated `v1.2` / `v1.3` forms. That will be normalized
when the changelog is moved out of source (scheduled for v1.21); the source is not being edited for
this alone.

| Version | State | Content |
|---|---|---|
| v1.00 – v1.09.4 | superseded | manuscript-era development line; Score B implemented at v1.09; dead-code cleanup and deep review at v1.09.1–v1.09.3 |
| **v1.10** | **current, stable** | macOS Tkinter crash class resolved; full pipeline confirmed executable on both Windows (pinned package set) and macOS (Python 3.12+, current packages) |
| v1.20 | planned | tree selection / display logic; further scope under discussion (§8) |
| v1.21 | planned | code-block cleanup; migrate the in-source changelog to the wiki and version files |
| v1.30 | planned | multiple methods per sample — depends on v1.20 landing first |

## 5. Architecture at a glance

```
RAW / mzML
    │   msprawextractor.py (Windows) · mzmlreader.py (cross-platform)
    ▼
MS2-indexed spectral tables (CSV/TSV)
    │
    ├── Route A — Constraint-based Glycan Annotation (CGA)
    │     compnewv4.py → in-silico composition library
    │     msp_insilicomarker_withGPT.py → ion matching, Score A
    │     msp_CGA_structscore.py → Score B re-ranking (optional)
    │
    └── Route B — Manual Annotation Support (MAS)
          mspvalidator_merger.py → expert annotations merged to MS2 index
    ▼
Selected-fragment-ion feature matrix     [transform: log10(I) + 1]
    ▼
Local Random Forest (scikit-learn)  →  .skops model + training_run.json
    ▼
Scan-level predictions + prediction report
```

Both routes emit the same feature-matrix contract, so training data from manual and
constraint-based annotation can be combined. Nothing leaves the local machine at any stage.

## 7. Known limitations and scope boundaries of v1.10

Stated plainly. Some of these are genuine limitations awaiting work; others are deliberate scope
boundaries of an MS2-centric tool and are recorded here so that they are not mistaken for oversights.

**Marker:** ▶ has a corresponding theme in §8.

1. **Fragment-ion features encode absolute intensity.** The feature transform is `log10(I) + 1` on
   vendor-reported intensity. Scans are identified by a UID derived from the source spectral file
   and MS2 scan number, and the feature matrix — optionally with protonated mass — is what the
   classifier sees.
   Per-spectrum or cross-sample intensity normalization is **not** applied, and this is a
   considered position rather than an omission: normalization presumes either comparable loaded
   sample amounts or in-run calibration standards. Many real acquisition protocols provide neither —
   calibration is commonly performed per experimental batch, not per sample — so a normalization
   step that is sound in principle becomes an ideal-condition assumption that does not hold for the
   data such a tool actually receives. Cross-sample comparisons should be read with this in mind.
2. ▶ **No peak-level denoising.** Peaks pass through as centroided by the vendor software. Whether
   to offer optional filtering is still an open question (T11).
3. ▶ **MS1 survey scans are not used.** GlycoMSP is an MS2-centric tool. MS1-based total-ion-current
   functionality and isotopic-envelope comparison are not part of the design, and adding them would
   require a change at the ingestion layer. One narrower case *is* planned as a v1.20 good-to-have
   (T9): matching a precursor against the M+1 isotopologue window as well as the assumed
   monoisotopic peak. That operates on the precursor mass and does not require MS1 envelope data, so
   it narrows this boundary rather than removing it.
4. ▶ **No derivatization-mismatch guard at prediction time.** A model trained on one derivatization
   chemistry will accept input of another and silently produce degenerate features. Users must keep
   chemistry consistent between training and prediction; `training_run.json` records what was used.
   A temporary guard is planned for v1.20 (T5); the complete check depends on ML artefacts being
   merged into the Dataset Explorer.
5. ▶ **Constraint-based library generation is time-consuming for large compositional spaces.**
   This is a limitation in absolute terms rather than relative to comparable tools. Constraint-based
   enumeration is what keeps the candidate set tractable at all — it enumerates biosynthetically
   plausible compositions rather than every mass-feasible one. GlycoGenius provides in-silico library
   generation at a **similar level**: under equivalent settings the two produce comparable numbers of
   candidates, although it is built around an MS1/EIC-based workflow rather than an MS2-centric one.
   In internal testing on the same machine, GlycoMSP completed generation in less time. The
   limitation is therefore absolute generation time on large compositional spaces — not candidate
   quality, and not standing relative to peer tools. Performance work is carried as a v1.20
   good-to-have (T10).
6. ▶ **External glycan identifiers are not resolved automatically.** Four integration points are
   reserved in source for a composition-resolution API; none is active in v1.10, and GlyTouCan ID
   and WURCS values are user-supplied. Addressing this is planned for v1.20 (T1).
7. **One label per MS2 scan.** This is a limitation and a design premise at once. Classification-based
   machine learning requires a single target per training example, so GlycoMSP's framework assigns
   the winning composition or structure to each MS2 scan and that assignment is what enters training
   and prediction. Spectra carrying evidence of more than one structure cannot be represented under
   this formulation.
8. **MS3 spectra are extracted but not consumed** by any v1.10 workflow. MS3 acquisition strategies
   for glycomics are heavily and manually defined per instrument and per laboratory, and are fixed
   at acquisition time — before any analysis software is involved. Generic MS3 support is therefore
   outside the current scope; it would be reconsidered only in the context of a specific
   laboratory workflow.
9. **Thermo RAW conversion requires Windows.** This follows from the vendor library that reads the
   proprietary format, not from a GlycoMSP design decision. mzML is the cross-platform path, and the
   remainder of the pipeline runs on Windows and macOS alike.

## 8. v1.20 development plan

> **Status: scoped, not frozen.** The themes below were settled in a project discussion on
> 2026-08-24 and are the working plan. They are not yet commitments with dates: each is still to be
> re-verified against the current source before implementation, and §8.2 in particular is explicitly
> droppable. Items may still be split or deferred, and reviewer feedback on the manuscript could
> reorder them.

**Governing principle (proposed):** *additive by default.* New behaviour should ship behind explicit
options with v1.10 defaults preserved, so that results produced with v1.10 remain reproducible under
v1.20. Where a change must alter default behaviour, it is re-run and re-reported rather than silently
adopted.

### 8.1 Planned for v1.20

| # | Theme | What it delivers | Addresses |
|---|---|---|---|
| **T1** | **External identifier annotation — GlyTouCan accession and WURCS** | Annotate assignments with GlyTouCan accessions and WURCS alongside the composition string. Four integration points are already reserved in source, and the target endpoint is publicly documented and requires no credentials. **Design:** an **offline reference cache is consulted first**, and the API is called only for compositions the cache does not hold; successful results are appended back. The cache schema must allow a composition to resolve to **zero, one, or many** candidate accession/WURCS records. Requests are kept deliberately light — batches of no more than ~30 structures with a pause between them. **Open choice:** enrichment at library-generation time (fewer downstream steps, but fetches compositions that may never be used) versus post-annotation lazy enrichment (far fewer calls, but adds an enrichment stage). To be settled at implementation. | §7.6 |
| **T2** | **Example datasets** | Two bundles ship with v1.20. **(a) A curated real subset** — permethylated N-glycans with a representative set of compositions plus manually selected non-glycan spectra, so users see genuine LC-MS/MS behaviour and the difference real negatives make. **(b) A synthetic set** — deterministic spectra carrying predefined fragment peaks in GlycoMSP's input format, so any correctly installed instance reproduces the same output. Realism is explicitly *not* the goal of (b). **Boundary written into the artefact: synthetic data is for installation verification, tutorials and regression testing only, never for performance claims.** | §7 |
| **T3** | **Public-data exploration workflow for non-MS researchers** | A documented route by which a biologist can evaluate whether glycan analysis is relevant to their question *before* committing to an experiment: locate a public deposit matching their biological model, check its chemistry and instrument, run CGA exploratory analysis over it, and interpret the candidates against the source publication. Shipped with an explicit **"not yet fully validated"** notice. | §7 |
| **T4** | **Dataset Explorer and project tree** | Make the explorer behave as a normal application: correct the tree selection and display logic, allow attributes, names and items to be renamed, removed, edited and viewed on each node, expose parameters and metadata in the interface, and **allow multiple CGA/MAS methods under one sample**. *(The in-source changelog assigned multi-method support to v1.30; it is pulled forward here.)* | usability |
| **T5** | **Training/prediction chemistry consistency** | Warn when a model is applied to data of a different derivatization chemistry than it was trained on. **Constraint:** training consumes only the trainable CSV, with no metadata or method JSON required at that point, so there is nothing authoritative to compare against yet. v1.20 therefore ships a **temporary guard** that warns on what can be inferred; the full check depends on ML artefacts being merged into the Explorer. The same work makes explicit what is already true in principle — other ionisation modes and derivatization chemistries are supported provided a properly defined fragment-ion list is supplied. | §7.4 |
| **T6** | **Multi-vendor input support** | Broaden ingestion beyond Thermo so that GlycoMSP is not bound to one vendor. Driven by the need to evaluate public deposits acquired on other platforms. | §7.9 |
| **T7** | **N-glycan hybrid logic** | Complete the unfinished hybrid branch in constraint-based generation. It currently misses only one or two minor compositions, but the gap is real and closing it is inexpensive. | capability |
| **T8** | **Feature-value validation** | Reject out-of-domain intensity values with a clear warning rather than passing them into the transform. Covers degenerate inputs and the no-match sentinel. | robustness |

### 8.3 Already addressed — not carried into v1.20

Recorded so that the roadmap does not promise work that is already done.

- **Ion-matching consistency — resolved.** Matching tolerances are consistent and documented:
  **20 ppm for precursor (MS1) matching, 10 ppm for fragment-ion matching.**
- **User documentation — published.** The user manual ships with the repository under
  [`docs/`](docs/) in both Markdown and PDF form, alongside the Score B design note. The internal
  developer wiki is a separate artefact and still carries pre-freeze drift — see §11.
- **Mass versus fragment evidence — examined.** The relative contribution of the precursor-mass
  constraint and of fragment evidence has been tested independently of the main analyses, and the
  test is reproducible on demand. Relaxing the precursor-mass constraint produced a comparable but
  slightly lower F1 and a lower precision: spectra whose precursor mass does not match are then
  admitted and annotated incorrectly. The interpretation is not clear-cut — a human annotator also
  judges a spectrum by its precursor mass before anything else — and GlycoMSP's design assumption is
  to reject precursor masses that do not match. The result has not been formalized into tables.

### 8.4 Evidence and external validation

| # | Theme | What it answers | Status |
|---|---|---|---|
| **T12** | **Comparison against other tools** | How does GlycoMSP stand against comparable software? The comparison is deliberately narrow — **one commercial and one open-source** tool — rather than a broad survey. | **Planned; licence enquiry outstanding.** The comparison axes differ by tool and must be designed before anything is run: some tools report assignments per spectrum, others at the chromatographic-feature level, so a single metric set cannot be applied uniformly. A pilot precedes any full comparison. |
| **T13** | **External validation against public deposits** | Can CGA assignments be evaluated against public deposits whose source publications carry annotations? Scope is deliberately narrow: **CGA evaluation only**, against the annotations reported in the source publication — not the full pipeline. | **Planned.** Deposits are selected for **derivatization-chemistry coverage** rather than volume: one permethylated example is sufficient to demonstrate the primary chemistry, with the remainder chosen to show that other chemistries also work. Each candidate must be verified individually for chemistry, polarity and released-versus-conjugated status. Note that aggregated public corpora redistributing *preprocessed* spectra are not directly reusable — the preprocessing is baked in, so reuse means returning to the original deposits and re-extracting. |
| **T14** | **Score B weight calibration** | Is the limiting factor in Score B its rule weighting or its underlying design? Iterative optimization across datasets separates the two. | **Planned, not urgent for v1.20.** Working hypothesis: a stable optimal weight set exists per condition — same method, ion mode, derivatization and comparable acquisition settings. **Convergence** would yield a condition-specific, calibratable scoring profile; **divergence** would indicate that the features are too dataset-specific or that the objective function needs redesign. The objective function is not yet defined. **Independent of T1** — WURCS annotation does not depend on this work. |

**Explicitly not in v1.20**

- **Per-spectrum or cross-sample intensity normalization** — not planned, for the reason given in
  §7.1: it assumes acquisition conditions that real datasets frequently do not meet.
- **Biosynthesis-driven or gene-expression-driven candidate generation** — **not pursued.** This is
  the subject of separate active research elsewhere in the field; GlycoMSP will monitor and cite
  rather than reimplement it. See §9.
- **Machine learning applied directly to WURCS** — no structural embeddings, no structure-inference
  decoding, no WURCS-derived features. WURCS is carried as an *annotation* in v1.20. Anything further
  is a long-horizon research programme, not a release item.
- **Broad code-block cleanup** and migration of the changelog out of source — scheduled for **v1.21**.
- **Generic MS3 / MSn support** — an acquisition-time, laboratory-specific concern; see §7.8.
  Deposits acquired as MSn experiments are deferred with it to **v1.30+**.
- **Peak-detection algorithm development, a web interface, and expansion to additional glycan
  classes** (glycosphingolipid, GPI) — out of scope for this line of development.

## 10. How v1.20 scope will be decided

Four inputs, in order of weight:

1. **Examiner feedback from the thesis defense**, and a follow-up discussion on 2026-08-24 — the
   scientific priorities take precedence over engineering convenience. Most of §8 originates there:
   external identifier annotation (T1), example datasets (T2), the public-data exploration workflow
   (T3), chemistry-context handling (T5), external validation (T13), and the tool comparison (T12).
2. **Manuscript review feedback**, if and when it arrives.
3. **An internal audit inventory** — every deferred item from the v1.10 freeze, plus findings from a
   comparative code audit conducted in August 2026, consolidated with source references and triaged
   individually.
4. **Independent adversarial review** — the practice used throughout the v1.10 freeze, in which
   patches in sensitive categories are reviewed by a second, independent reviewer before acceptance,
   with all outcomes recorded.
